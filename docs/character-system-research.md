# 角色系统：现状评估与资产制作调研

调研日期：2026-11-03。状态：研究结论与建议，尚未实现角色系统。

用户已确认：角色可以统一成可爱的运动员比例，不要求保留各角色原版身体比例。目标包括懒羊羊、海绵宝宝、功夫熊猫和兔子等不同外观。

## 1. 结论

继续使用 Three.js + GLB + 骨骼动画 + IK 是合适的，不需要为角色系统更换引擎。现有实现已经具备单人/双人显示、独立骨架克隆、左右手持拍、跑步动画混合、程序化步法和触球点 IK 等基础。

但当前实现属于“单个骨架驱动的程序化运动员”，还不是可替换模型的角色系统。直接替换 Xbot.glb 不足以接入新角色：原始蒙皮会被隐藏，材质会被改色，角色骨骼和比例也有固定假设。

推荐方向：**统一一套 Q 版双足运动员骨架与击球可达范围，离线制作不同外观的角色包，运行时选择角色并共用动作系统。** 第一版先让角色差异体现在头、体表、服装、耳朵和轮廓上，不增加角色能力差异。

“生成一张画像”和“得到可以打球的角色”是两个交付层次。PNG 可用于选角卡片；上场角色需要有网格、材质、骨骼、蒙皮权重和适配配置的 3D 资产。

| 资源服务 | server.js:78 | 已有 /models/ 静态目录，可承载角色 GLB、预览及配置 |

直接更换骨架还可能因为缺少必需骨骼，在 sports-kit.js 中解引用失败。应在构造角色前完成资产校验，并提供默认角色回退。

### 本次实际检查

- Xbot.glb 为 2,930,032 字节，含 1 套 67 关节骨架、2 个原始网格、7 个动画片段。
- 现有 PlayerView 的 16 个映射骨骼均能找到，idle/walk/run 片段均能匹配。
- 当前一个角色 root 中有 39 个可见 Mesh，约 12,926 个几何三角形，另有 2 个隐藏的蒙皮网格；地面软影另计。这里是对象/几何计数，不是实测 draw call 或帧率。
- npm test：52 项通过、0 失败；其中 rig.test.js 有左右手可达触球点和连续帧骨骼稳定性检查，共 3 项。
- 查看了项目已有 docs/rig-preview.png。它是已有动作预览，不作为本次浏览器实时画面或帧率验证。

总体评价：玩法驱动层值得保留；外观目前偏原型，身体部件连接、角色辨识度和动作风格还需要资产制作完善。分屏会执行两次场景渲染，新模型必须在实际分屏场景中评估性能。

## 3. 这些角色能否支持

以下难度是结合代码和角色形态的工程判断，尚未用这些角色的实际模型验证。

| 角色方向 | 建议处理 | 相对难点 |
| --- | --- | --- |
| 直立兔子运动员 | 标准双足身体 + 兔头、长耳、短尾 | 最适合首个样例；耳朵先跟头部整体运动，后续再加摆动 |
| 懒羊羊方向 | 共用运动员四肢，保留发型、脸型、羊毛、角等辨识特征 | 大头遮挡、羊毛体积及肩部穿插 |
| 功夫熊猫方向 | 共用骨架，做较圆的躯干、熊猫头和较粗四肢 | 腹部与手臂穿插、弓步和抬手时的蒙皮权重 |
| 海绵宝宝方向 | 保留方形轮廓，但明确肩、手肘、髋、膝、手腕位置 | 头身一体、细长四肢，不适合直接套当前头部追球/脊柱扭转；需要减少躯干扭转，或让方形身体作为整体随躯干运动 |
| 四足兔子/真实动物 | 不属于第一版共用双足角色 | 需要额外动作与持拍设计；“生成工具支持四足”不代表游戏动作系统已支持 |

统一比例意味着共享肩高、臂展和腿长的大致范围，不是把所有原版角色等比拉到同一高度。长耳、羊角、头顶毛不应参与有效身高计算。

角色可以共享骨架拓扑，但方形身体和圆胖身体仍可能需要不同的蒙皮权重、局部旋转限制和动作幅度。保留这种少量配置差异，比为每个角色复制一套 PlayerView 更容易维护。

## 4. 三条可选制作路线

| 路线 | 好处 | 代价/限制 | 建议 |
| --- | --- | --- | --- |
| 继续用程序几何拼角色 | 延续 sports-kit 的办法，制作简单兔子/方块角色快，容易共用现有骨架 | 美术细节和角色还原度有限；每种外观都要写几何代码 | 保留为默认角色、加载回退及早期验证 |
| AI 参考图→3D→统一骨架→GLB | 可扩展外观丰富，符合以后持续生成新角色的目标 | AI 输出需要挑选、清理、绑骨与变形检查，不能保证一次可用 | **推荐主路线** |
| 每个角色独立骨架和动作 | 最能保留原始比例与个性 | 接入、动作重定向及触球校准工作量最高 | 特殊角色或后续精品角色使用 |

用户已确认统一运动员比例；以上主路线仍是本次建议，不代表已经验证某家生成服务的成品质量。

## 5. 生成工具调研

仅根据官方文档核实能力，未付费生成、上传项目资产或进行工具间画质对比。服务能力及导出套餐可能变化，实际制作时以账户内显示为准。

### Tripo：建议优先做接入试验

官方提供图片/多视图生成、绑骨前兼容性检查和自动绑骨。Auto Rig 文档支持双足角色、Mixamo 命名规范及 GLB 输出；因此与当前项目的命名约定有较直接的衔接点。[Auto Rig 官方文档](https://developers.tripo3d.ai/en/docs/animations-rig)、[Rig Check 官方文档](https://developers.tripo3d.ai/en/docs/animations-rig-check)。

官方另有从单图生成多视图及多视图生成模型的接口，可用于减少手动补视图的工作。[Image to Multiview](https://developers.tripo3d.ai/en/docs/generation-image-to-multiview)、[Multiview to 3D](https://developers.tripo3d.ai/en/docs/generation-multiview-to-model/standard)。

注意：Mixamo 命名兼容只解决一部分接入问题，不保证与 Xbot 的绑定姿态、骨轴、长度和握拍方向完全一致。如果各角色分别自动绑骨，仍须归一化到项目的标准骨架/配置，并验收动作。

### Meshy：适合做备选和模型效果对比

支持单图及同一对象 1–4 张不同角度图片生成模型；文档提供 A/T pose、重建网格及 GLB 等输出选项。[单图 API](https://docs.meshy.ai/en/api/image-to-3d)、[多图 API](https://docs.meshy.ai/en/api/multi-image-to-3d)。

自动绑骨明确面向肢体和躯干清晰的标准双足人形，不能据此承诺所有夸张卡通角色都自动成功。生成的骨架可继续应用动画。[Rigging API](https://docs.meshy.ai/en/api/rigging)、[Animation API](https://docs.meshy.ai/en/api/animation)。

### Mixamo：可用的绑骨/基础动作补充

适合结构明确的双足人形，比例过度夸张或大型附属物会影响自动绑骨。Adobe FAQ 同时说明其账户地区限制，包括中国国家代码账户的限制，因此不宜作为本项目唯一依赖。[Adobe Mixamo FAQ](https://helpx.adobe.com/creative-cloud/faq/mixamo-faq.html)。

### Hunyuan3D：需要可控生成环境时再考虑

腾讯 Hunyuan3D-2.1 官方仓库提供图生形状与 PBR 纹理流程。这条输出是制作网格的起点，仍需单独完成角色骨架、权重和游戏接入。其官方公布的显存需求较高，本轮不建议先投入本地部署；后续若需批量生产或定制流程再评估。[官方仓库](https://github.com/Tencent-Hunyuan/Hunyuan3D-2.1)。

建议先拿同一张兔子参考图，在 Tripo 与 Meshy 中各生成一个候选，用本项目的持拍、抬手、弓步验收结果来选择工具。不能只比较静态预览图。

## 6. 以后怎样生成画像与角色

### 推荐流水线

角色描述 → 固定一张主设定图 → 基于主图补正/侧/背视图 → 图生 3D → 清理与减面 → 统一骨架与蒙皮 → 配置球拍握点与动作 → 导出 GLB → 项目预览验收 → 登记角色。

生成服务放在离线制作阶段。游戏运行时直接加载审核过的 GLB，不在每次选角时现场生成模型。

### 先做适合建模的图

- 全身直立、A pose 或 T pose，手臂与躯干分离、双腿分开，关节位置清楚。
- 使用单色背景、均匀光照，身体、耳朵和脚都完整入画，避免透视夸张、遮挡和戏剧化阴影。
- 先固定一个角色，再以它为参考编辑出侧面、背面；不要独立文字生成三张容易互相矛盾的图片。
- 三视图里衣服、颜色、耳朵形状、脸型、配件和身体比例要一致。多图接口应上传各自单独裁出的视图，避免把整张三视图排版当作一个模型输入。
- 不在建模参考图中握球拍；球拍由游戏挂到手上，避免生成时与手掌粘连。
- 角色定稿后，再制作头像、选角卡片与庆祝插画。头像不宜直接作为全身建模的唯一输入。

### 可复用的设定图提示词

> 为实时 3D 羽毛球游戏设计一个全身的 Q 版直立兔子运动员。统一运动员体型，约四头身，手臂和腿长度适中且关节位置清楚，肩部与手腕适合持拍，运动短袖、短裤和运动鞋。保留兔子的长耳、圆脸和短尾特征。身体比例便于复用双足人形骨架。A pose，双臂自然向两侧展开，手掌与躯干分离，双脚分开。正面、近正交视角，完整展示耳朵到脚底，纯浅灰背景，均匀柔光，清晰轮廓，简洁低多边形卡通 3D 风格。不拿球拍，不要文字、场景、底座或其他角色。

补侧面/背面时增加：

> 严格以这张已定稿角色图为参考，保留同一个角色的体型、服装、颜色和配件，只改变为侧面/背面近正交视角；姿势与尺度保持一致。

替换成羊/熊猫/海绵方向时，保持运动员四肢、站姿和关节约束，修改外观描述。海绵方向要特别写清楚“方形躯干、独立的双臂双腿、可辨识的肩肘髋膝关节”，并在后续绑骨时人工检查。

## 7. 建议的角色系统边界

### 三个相互独立的层次

1. **玩法角色**：服务端位置、输入、跑位、命中和得分。第一版各外观共享能力与判定参数。
2. **动作适配**：标准骨骼语义、绑定姿态、骨轴、IK、基础片段、挥拍与步法幅度、握拍坐标。
3. **视觉资产**：网格、贴图、头像、显示名、队色区域、耳朵/尾巴等附属物。

目前 PlayerView 同时承担这三层中的多种假设。接入时应保留其 IK 思路，逐步把运动员几何外观和 Xbot 专属配置移出。

### 每个角色包应包含什么

| 数据 | 用途 |
| --- | --- |
| id、显示名、版本、缩略图 | 选角展示与版本缓存 |
| modelUrl | 带材质和蒙皮的 GLB；尽量内嵌所需纹理 |
| rigProfile、boneMap | 标准骨架类型及语义骨骼映射 |
| scale、groundOffset、朝向 | 尺寸、脚底归零和面朝方向；有效身高不计耳朵等装饰 |
| 左右手 gripSocket | 握点位置、旋转、拍杆与拍面校准 |
| animationMap、motionProfile | 基础动作名称、步幅、重心、躯干/头部追球的幅度 |
| 材质保留及队色区域 | 保留角色辨识色，只替换衣服指定区域；也可使用脚下队色标记 |
| 来源、生成参数、授权记录 | 资产追溯与后续重制 |

这些是建议字段，不是当前已经存在的接口。

选角的最小闭环：手机选择已登记角色 → 服务端校验 characterId → 写入玩家状态 → 所有大屏按同一 id 加载 → 迟加入/刷新可恢复 → 加载失败回退默认角色。只传登记 id，不接收手机随意传来的模型 URL。

模型加载按 URL 缓存；每个玩家独立克隆骨架。更换角色时还需处理旧动画、材质、纹理、几何资源和异步加载竞争；共享资源不能在一方换角时被另一方错误释放。

### 为什么需要统一击球包络

服务端判定使用固定的逻辑拍心与半径，现有可见拍头通过 IK 尝试靠近权威触球点；超出臂长时腕部会被限制，所以不是任何外形都能精确够到所有命中点。

第一版建议保持相近的肩高、臂长和持拍范围，通过头部、宽度、材质和配件表现角色差异。基准 Q 版骨架需要先在服务端允许的典型触球位置完成校准，再批量制作其他外观。不要只把人物缩小而保留成人挥拍轨迹。

如果最终允许明显不同的身体高度，就需要另行决定统一的卡通伸展补偿，或调整所有角色共同的击球范围；这会影响动作与玩法，不属于免费换皮的结果。

## 8. 接入时需要处理的改造点

1. 将 screen.js 的单个 MODEL_URL 改为角色登记与按玩家 id 加载。
2. 将 sports-kit 作为默认/回退外观，取消对所有外部角色无条件调用它。
3. 外部角色保留原始蒙皮和材质；按配置修改指定队色区域。
4. 在加载后校验必需骨骼、蒙皮及有限数值，缺失时回退，避免到 update 时才崩溃。
5. 从 Xbot 成人骨架迁移到一套明确的 Q 版基准骨架，基础动画重定向并校准；骨骼同名不代表骨轴相同。
6. 把挥拍高度、自由手目标、落脚宽度、重心变化、握拍姿态等绝对常量纳入比例/动作配置。
7. 在网络加入角色选择、状态同步与恢复；本轮建议先在开局前选角，避免比赛中切换资源干扰。
8. 增加角色预览验收入口，能看正侧背面、待机、移动、左右手挥拍与触球误差。

若导出压缩模型，需要额外配置解码器。当前 loadPlayerGLTF 没有注册 Draco、KTX2、Meshopt 解码支持，不能假定任意压缩 GLB 都能直接加载。Three.js 官方说明了相应的设置接口。[GLTFLoader](https://threejs.org/docs/pages/GLTFLoader.html)。现有 SkeletonUtils 还提供重定向能力，但项目目前仅使用了 clone；是否选用运行时或离线重定向，需要用基准角色验证。[SkeletonUtils](https://threejs.org/docs/pages/module-SkeletonUtils.html)。

## 9. 第一版资产目标与验收

以下为建议起点，不是实测性能上限：

- 运行时使用 GLB，Y 向上、面朝 +Z，脚底归零；制作源文件另存。
- 共用一套 Q 版双足骨架与绑定姿态，骨轴和左右手握点有统一约定。
- 单角色约 1–3 万三角形、1–3 个主要材质，纹理从 1K–2K 起步；按可见效果决定是否增加。
- GLB 尽量控制在 3–8 MB，超过后检查几何与纹理；体积小不等于显存占用小。
- 基础动作使用原地移动版本，避免片段根位移与服务端位置重复叠加。
- 毛发、羊毛优先使用几何轮廓与纹理，耳朵/尾巴先作为静态附件，后续再加少量附属骨骼。

验收必须覆盖：正侧背面辨识度、手臂抬高时肩部、熊猫腹部与前臂穿插、海绵躯干扭转、左右手拍面朝向、脚底贴地、典型高低/左右触球点、单人和双人分屏，以及换角/加载失败/刷新恢复。

现有 rig.test.js 只证明 Xbot 的一个可达触球点和骨骼稳定性；新角色需要复用并扩展这类检查，同时人工看实际变形。目标是让典型有效命中在画面上确实碰到拍面，而不是只看到服务端判定成功。

## 10. 推荐验证顺序

先完成“默认运动员 + 一只 Q 版兔子”的双角色试验：确定基准骨架、保留真实模型外观、完成选角同步、校准左右手及挥拍。

兔子是推荐样例，因为它既能验证动物特征，又保留清晰双足结构。通过后制作羊和熊猫；最后用方形海绵身体检验动作配置是否足够灵活。若只做兔子，无法证明所有特殊体型已经兼容。

首轮试验产出应包括一个真正能打球的 GLB、对应角色配置、选角卡片，以及动作/性能验收记录。用这套结果确定工具和规范后，再批量生成角色。
