# 手机手柄 App 与连接方案

## 1. 背景与问题

当前形态是「PC 跑服务 + 手机浏览器 ctrl.html 当球拍」，手机必须能通过局域网访问电脑的 3100/3543 端口。

办公网络下出现过两类阻塞：

- 电脑与手机由 DHCP 分到不同地址（如 `192.168.74.254` 与 `192.168.79.x`），虽有可能是同一 `/20` 网段，但公司 WiFi 普遍开启终端隔离（AP isolation），手机到电脑的入站连接不通。
- 仓库不携带证书，早期只启动了 HTTP，而二维码指向 `https://IP:3543`，手机必然打不开。

已落地的兼容改动（见 `server.js`、`public/index.html`）：

- 证书缺失时自动生成自签证书到 `certs/`，HTTPS 3543 常开。
- 网卡地址改为实时枚举，排除 `169.254.*`，优先无线/以太网。
- 手机连接面板支持在多网卡间切换二维码（WLAN / 蓝牙网络连接 / 热点）。

## 2. 目标与边界

目标：

- 在公司网络不可直连的条件下，手机仍能作为体感球拍使用。
- 手感损失可控，挥拍判定与现有规则保持一致。

非目标：

- 不做公网中转/云服务（额外延迟、成本与运维）。
- 不改变服务端权威判定与现有 Socket 事件语义。

## 3. 连接方式对比

| 方式 | 需要装 App | 依赖公司网络 | 额外条件 | 端到端延迟（经验值） | 平台限制 |
| --- | --- | --- | --- | --- | --- |
| 网页 + WiFi 直连 | 否 | 是 | 同网段且未隔离 | 30–50ms | 无 |
| 蓝牙网络共享（PAN） | 否 | 否 | 手机开「蓝牙网络共享」，电脑连接「接入点」 | 60–100ms | 安卓 |
| USB + `adb reverse` | 否 | 否 | 数据线 + USB 调试 + adb | 30–50ms | 安卓 |
| App + WebSocket | 是 | 视网络 | 热点/直连/USB 反向 | 30–50ms | 安卓/iOS |
| App + 蓝牙 SPP | 是 | 否 | 蓝牙配对，Windows 虚拟 COM 口 | 60–100ms | 安卓（iOS 无 SPP） |
| App + BLE GATT | 是 | 否 | PC 需做 BLE 外设，Windows 支持差 | 40–80ms，抖动大 | 不推荐 |

结论：纯蓝牙直连（配对后不开启网络共享）只有原生 App 能实现，浏览器拿不到 RFCOMM/SPP 通道；蓝牙上唯一能承载 IP 的协议栈就是 PAN，也就是「蓝牙网络共享」开关。

## 4. 推荐方案：WebView 壳 + 原生传感器/蓝牙 + 双通道

复用现有手柄页的 UI、校准与挥拍识别逻辑，只把「传感器采集」和「数据发送」下沉到原生，做到两条通道自动切换：

```text
Android App (Kotlin)
  ├─ SensorManager 50–100Hz → 姿态融合 → 30Hz pose
  ├─ 挥拍识别（复用 ctrl.html 算法）
  ├─ 震动反馈 / 屏幕常亮 / 前台服务保活
  ├─ 通道 A：WebSocket(Socket.IO) ──▶ server.js
  └─ 通道 B：RFCOMM(SPP) ──▶ Windows COM ──▶ bridge/spp-bridge.js ──▶ Socket.IO
                                                        │
大屏 index.html ◀── state(60Hz) ── server.js ◀──────────┘
```

通道选择优先级：WebSocket 可用则优先（延迟最低）；不可用时回退 SPP。

## 5. 协议设计

### 5.1 WebSocket 通道

直接复用现有事件，无需新协议：

- 上行：`ctrl:join`、`ctrl:pose`、`ctrl:swing`、`ctrl:hand`
- 下行：`ctrl:joined`、`ctrl:tick`、`ctrl:hit`、`ctrl:miss`

### 5.2 SPP 通道（NDJSON）

一行一个 JSON（UTF-8，`\n` 结尾），与 Socket 事件字段保持一致，便于桥接复用判定逻辑：

| 类型 | 字段 | 说明 |
| --- | --- | --- |
| `join` | `slot?`, `hand?` | 申请场地 |
| `pose` | `q:[x,y,z,w]` | 姿态四元数，30Hz |
| `swing` | `power`, `dir`, `lift`, `shot`, `peak` | 挥拍 |
| `hand` | `hand` | 切换持拍手 |
| `ping` | `t` | 1s 心跳，用于断线检测 |

桥接侧把 `pose`/`swing` 映射为同名 Socket 事件即可，服务端判定逻辑零改动。

### 5.3 可靠性

- 心跳 1s，3 次未收到判定断线；重连退避 500ms → 1s → 2s（上限 5s）。
- 姿态包为「最新值覆盖」语义，允许丢弃；挥拍包必须送达，失败重发一次。
- 连接建立后 App 主动发 `join`，服务端按现有逻辑分配左右场地。

## 6. 延迟预算与手感

| 环节 | 耗时 |
| --- | --- |
| 传感器采样 + 融合 | 10–20ms |
| 本地挥拍判定 | ≈0（事件触发即发） |
| WiFi/热点/USB 传输 | 2–10ms |
| 蓝牙 SPP 传输 | 20–60ms（抖动偏大） |
| 服务端 60Hz 循环排队 | 0–16ms |
| 渲染 | 0–16ms |

- WiFi/热点/USB：端到端约 30–50ms，跟手。
- 蓝牙 SPP：约 60–100ms，可玩，杀球时机略钝。
- 服务端挥拍窗口为 300ms，100ms 内延迟不会漏球，超过 150ms 才会出现「挥了没反应」。
- 带宽不是瓶颈：30Hz × 约 60B ≈ 1.8KB/s，蓝牙 3Mbps 足够；真正影响体验的是抖动与重连。

## 7. 工程改动清单

PC 端：

- 新增 `bridge/spp-bridge.js`：`serialport` 读取 NDJSON → 调用与 Socket 相同的处理函数；支持 `--port COMx` 与自动探测。
- `package.json` 增加 `serialport` 依赖与 `npm run spp` 脚本。
- `server.js` 把 Socket 事件处理抽成可复用的 dispatch 函数，供桥接调用（判定逻辑不变）。

Android 端：

- WebView 载入现有 `ctrl` 页面，注入 JS Bridge。
- 原生传感器采样与挥拍判定（复用现有算法），原生蓝牙发送。
- 前台服务保活、`FLAG_KEEP_SCREEN_ON`、震动反馈。
- 打包签名 APK，支持侧载安装。

兼容性：

- 走 SPP 时不需要 HTTPS；走 WebSocket 时沿用现有自签证书。
- 服务端无需修改任何物理/判定代码。

## 8. 风险与限制

- iOS 无 SPP，只能 BLE 或 WiFi，跨平台成本陡增。
- Windows 蓝牙虚拟串口存在配对/驱动/COM 口变动问题，需要重连与端口选择 UI。
- 蓝牙链路抖动明显，快速连续挥拍可能出现事件乱序（需序号字段兜底）。
- 双端维护成本：APK 分发、签名、版本兼容。
- 公司电脑若限制安装驱动，SPP 桥可能无法落地；当前 Node 方案不受影响。

## 9. 里程碑与验收

1. PC 端 SPP 桥 + 手机串口工具（不写 App）打通：能发 `pose`/`swing`，大屏有反应。
2. WebView 壳 + 原生传感器，WebSocket 通道跑通。
3. 蓝牙 SPP 通道跑通，双通道自动切换。
4. 手感验收：连续 20 拍不漏击；杀球/吊球判定与网页手柄一致；断线 3s 内自动恢复。

## 10. 不写 App 的快速替代

- 手机热点：电脑连手机热点，两端同网段直连，延迟最低。
- USB + `adb reverse`：`adb reverse tcp:3100 tcp:3100` 后手机打开 `http://localhost:3100/ctrl`；`localhost` 属于安全上下文，传感器可用且无证书警告。
- 蓝牙网络共享（PAN）：免安装 App，但依赖手机「蓝牙网络共享」开关。
- 键盘单机：空格 = 玩家 1 挥拍，回车 = 玩家 2，A/D 与 J/L 控制落点。
